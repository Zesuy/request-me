# request-me：设计与实施说明

更新于 2026-09-08。本文记录当前产品共识，供后续会话直接继续设计与实施；当前实现协议见 PROTOCOL.md，真实联调结果见 LIVE.md。

## 产品核心

request-me 将人作为异步调用的一方。Agent 在需要人提供信息、选择方向或完成现实操作时交接工作；人的回答随后成为原 Codex 会话的新一轮输入。通知用于传递进展和结果。

首版聚焦 QQ 与 Codex，服务端、MCP、Bridge 在同一仓库维护并分别部署。MCP 与 Bridge 由同一个 Node.js 包提供，安装后暴露两个独立命令；QQ 服务端使用 Python/NoneBot。洗浴继续在自己的项目维护，其他 Agent 和邮件确认留待后续实际需求。

外部业务通过配置化 HTTP 应用接入：Bot 根据命令配置路由到应用，应用返回 Markdown、动作按钮和上下文；点击事件根据保存的卡片归属回到同一个应用。业务操作卡片与人工请求分别处理。Bath 的 HTTP 客户端、状态解释和呈现由 `xiaoding-bath-server` 中的独立接入端负责。具体契约见 [APPLICATIONS.md](APPLICATIONS.md)。

## 用户原话：request_human 的用途

> request human应当被用于：按你的要求做了xxx，但发现xxx（很重要的信息），我没有擅自xxx，接下来我们应该xxx？，然后可以随他心意给出abc选项，或者不给选项直接给让他回复。或者：我们本应xxx，但我发现xxx，我尝试了xxx，但最后发现无法xxx。接下来我应该？abc。或者说，我尝试了xxx，现在xxx状态如何，就等你xxx（比如说操作物理设备重新连接等），当你xxx完成后点击按钮我会重新开始检查。同样的，话说如果人不想回复，我们应该？

## 工作交接体验

Agent 自由组织完整正文，交代做过的工作、重要发现、停下来的原因和需要用户提供的帮助。按问题选择提供快捷选项或仅接受文字，始终支持自由回答。

例如：

> 已完成配置并验证接口，但设备仍然离线。我尝试重新连接两次，发现 USB 连接没有恢复。请重新插拔设备，完成后点击下面的按钮，我会再次检查。
>
> [已经重新连接，请检查] [暂时结束]

按钮值表达用户的回答。Codex 结合原会话上下文决定下一步：继续执行、补充调查、调整方案或结束。物理操作场景以用户确认完成作为恢复检查的触发。

正文使用 Markdown，链接、表格、代码块保留在其中；QQ 转换在发送层完成。选项使用原生按钮事件，人工输入按钮填入输入框后由用户编辑并发送。消息直接呈现有信息量的正文、来源和选项。

## 用户暂时或永久离开

| 用户行为 | 语义 |
| --- | --- |
| 暂时忽略 | 请求保持待答；Agent 已结束当前轮，用户可以稍后回来回答 |
| 关闭请求 | 收起待答事项，保留记录与原会话；Codex 保持当前停下来的状态 |
| 回答“结束”或给出新方向 | 作为实际用户输入投递给原会话，由 Codex 处理 |

沉默保留为待答状态。提醒、定时检查按用户明确提出的需要安排。关闭请求属于产品交互，与提交给 Codex 的回答分别处理。

## 多对一部署与会话关联

一个长期运行的 QQ 服务端连接多个独立 Bridge；每个 Bridge 可以服务多个 Codex 会话。MCP 随 Codex 调用运行，Bridge 常驻。

固定关联关系为：

```text
人工请求 ID → Bridge 实例 ID → Codex 会话 ID
```

服务端根据凭据识别 Bridge，保存请求归属；MCP/Bridge 自动取得并维护 Codex 会话关联。QQ 上显示项目、会话名称和主机等简短来源信息。

发送时由 MCP 集成层自动补齐来源：从逐次调用元数据取得 thread ID，通过对应 Codex app-server 的 `thread/read` 读取会话标题和目录，优先采用可验证的当前调用目录。目录按所在执行主机的路径语义解析；展示项目简称，需要区分时补充路径。会话目录与项目根目录分别标记。

QQ 来源行示例：`检查设备连接 · tmp · WSL`。标题尚未生成时展示项目和主机，获取到的来源随请求保存。标题与目录用于识别工作上下文，内部 ID 负责回程定位。该补全流程列入首版实现验证；[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)提供会话信息读取接口，原型已验证的 MCP 元数据目前主要是路由标识。

选项与人工输入都必须明确关联到具体请求。多问题并存时，优先利用可验证的 QQ 引用关系；需要时在预填输入中使用简短关联码，解析后再把正文交给 Codex。具体交互形式在协议与 QQ 验证阶段确定。

## 协议与时序

使用小型 HTTP JSON 契约，保留两个操作：

- `request_user_response`：完整 Markdown、可选答案、自由输入设置、请求标识与内部路由关联。
- `send_user_notification`：发送进展或结果，返回发送回执。

正文与选项由 Agent 提供；Bridge 身份和会话路由由集成层补齐。字段名与接口路径在协议草案中定稿。

一次人工交接的流程：

1. Codex 在结束当前轮前调用 MCP，发送问题。
2. QQ 接受消息后，MCP 返回发送成功，Codex finish。
3. 用户选择或输入，服务端保存对应请求的回答。
4. 原 Bridge 通过长轮询领取回答，调用 `codex queue`，将回答作为原会话的新 user message。
5. Bridge 回报投递结果，Codex 根据回答继续工作。

按钮的“已提交”表示回答已进入收件箱。系统记录投递回执，仅在失败或结果不确定时通知用户。Codex 根据任务需要发送实际进展或最终结果。

## 近期实施与验收

1. 定义请求、回答、关闭请求及投递回执的最小协议，确定 Bridge 与会话关联方式。
2. 从原型提取 QQ 连接、Markdown、原生按钮、人工输入和已有重复请求处理。
3. 实现 Node.js MCP 与常驻 Bridge，接通 QQ → 原 Codex 会话的回答回程。
4. 验证两个 Bridge、多个会话同时提问，按钮和文字分别回到正确会话。
5. 验证待答、关闭、投递成功与失败反馈，以及回答后继续工作、发送结果或再次提问的完整体验。

当前优先完善正常运行中的交互体验与准确路由。原型已有请求去重和重复点击提示；服务端与 Bridge 重启恢复、进一步的安全与可靠性完善列为后续专项。
